# V2 budget and restaurant recommendation

V2 guests accept low, medium, and/or high price bands. These are coarse menu-price tiers, not quoted pound amounts or guarantees about drinks/service charges. A missing legacy budget answer defaults to medium. Only included attending guests participate in the intersection. One common tier can be selected automatically; several require an organiser choice. With no common tier, the organiser must explicitly override before proceeding. Overrides do not override cuisine vetoes or dietary contradictions.

The restaurant provider uses the selected tier for both area feasibility and restaurant suggestions. Unknown prices are excluded from V2 budget matches and suggestions. Area feasibility may retain otherwise suitable unknown-price venues with an explicit unverified-price caveat, so the organiser can reach the manual venue path; known incompatible prices are excluded. This does not count an unknown price as a verified match; V1 still includes unknown prices and excludes high prices. Area fairness ordering is unchanged: worst outward/return journey, spread, total, stable ID. The price filter is feasibility, not a fairness score.

The single recommendation is deterministic, using the existing cuisine-ranked order. It requires evidence checked within seven days, explicitly covering the entire selected dinner interval, the exact price tier and every structured food requirement. Cuisine vetoes are rechecked. Free-text food requirements force manual verification. Live evidence must come from a venue and have an HTTPS source; synthetic fixture evidence works only for fixture dinners. Merely having a menu link, OSM tag, or hours string does not establish these facts. Missing, stale, future-dated, incomplete or mismatched evidence produces an explicit V1 shortlist/manual fallback message. A recommendation neither chooses the restaurant nor confirms the dinner; those remain organiser actions.

## Provider limits

Current live OpenStreetMap results report price as unknown. Their opening-hours strings are displayed verbatim with a verification warning; there is no reliable selected-date parser or date-specific opening verification. OSM diet tags are reported claims, not venue verification. Consequently the current live provider cannot produce a supported V2 single recommendation and retains unknown-price area candidates only with a visible caveat; it returns no verified-price restaurant suggestions. The organiser can use the existing V1 flow/manual venue path and verify directly. No fallback silently switches to fictional data.

Fixture dinners use visibly named fictional restaurants and synthetic price, selected-date opening and diet evidence. The configured data mode remains fixture; this is a demonstration/test of the flow, never evidence about a real restaurant. No LLM, paid provider, reservation API, origin or contact sharing is involved.
