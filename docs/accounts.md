# Email accounts and personal invitations (V2)

Existing dinners retain browser-based V1 identity. New account dinners require `ENABLE_V2=true`, `experience: "v2"`, `identityMode: "account"`, an existing pilot creator permission, a verified account and one `inviteEmails` entry per guest name. Turning the flag off stops creation; it does not change existing account dinners.

The default and only authentication adapter is Supabase email OTP. Set server-only `SUPABASE_URL` (HTTPS) and `SUPABASE_ANON_KEY`. No service role key is needed. Configure the provider's email template to show `{{ .Token }}`; its default magic link template is not the code entry flow. Enable and configure the provider email rate limits and production SMTP before inviting real users. No accounts are created until someone explicitly requests a code. There is no local fixture sign-in bypass. The optional browser contract harness described below starts a separate local HTTPS provider double; the application still performs its normal server-side provider verification.

Apply migration `003_accounts.sql` using the normal migration procedure. Account tables have RLS enabled and no browser policies; application access uses the server Postgres connection. Session records contain sensitive provider access tokens and must receive the same protection as database credentials and backups.

Visit `/account` to request and verify a code. Session cookies are opaque, Secure, HttpOnly and SameSite=Lax. Every request checks the server-side session expiry and disabled state, then verifies the provider user and confirmed email over HTTPS. Provider access tokens never reach browser JavaScript. A session lasts at most one hour and never exceeds the provider expiry. There is deliberately no automatic refresh: expired sessions ask the user to verify again. Local manual verification needs HTTPS (or the browser's localhost Secure-cookie support).

The creator receives private per-guest links on creation. `dinnerAction(id, {type: 'issue-invite', guestId})` replaces a pending guest's link and returns `invitationLinks`; `revoke-invite` revokes it. Invitation links should be delivered only to the intended person. Each link is random, hashed in storage, bound to the guest's normalised verified email, valid for seven days at most (also capped by dinner expiry and reply deadline), and single use. Issuance and redemption use the dinner row lock, so parallel attempts cannot both claim. Pending names cannot be claimed from the shared URL. Claimed identity follows the verified provider account to other devices; browser claim and organiser cookies grant no access to account dinners.

An organiser must reset a claimed guest before issuing a replacement. Reset clears account identity, reply and delivery claim generation, deletes subscriptions through the existing store transaction, and revokes outstanding invitations. Public DinnerView never includes account IDs, raw invite contacts or invite token hashes. Only organiser action responses contain freshly created raw links; they are never read back from stored hashes.

Sign out revokes the current device session. Disable account revokes every device, prevents future sign-in and removes matching dinner email subscriptions, including separately verified contact addresses attached to that account's guest identities. Registration and delivery lock and recheck the account's active state, so an in-flight request cannot restore updates after disable. Separate creator waitlist consent remains independent. This is an application account disable, not deletion of the user's identity at Supabase; existing dinner contributions remain until the dinner expires. The account UI explains this before confirmation. Deleting the provider identity also fails future provider verification.

Verification: account model tests cover contact mismatch, expiry, revocation, replay, two-account isolation, cross-device identity and V1 boundary. Provider tests use a mocked network, separate from fixtures. They do not assert live email delivery. Real inbox OTP delivery, actual Supabase account lifecycle and HTTPS browser cookie behaviour require a configured provider and human inbox verification.

Provider contracts: [Email OTP](https://supabase.com/docs/guides/auth/auth-email-passwordless), [verifyOtp](https://supabase.com/docs/reference/javascript/auth-verifyotp), [getUser](https://supabase.com/docs/reference/javascript/auth-getuser).

## Local browser contract test

Run `pnpm build`, then `pnpm test:e2e:auth` against a disposable, migrated local database (`DATABASE_URL` from your environment or ignored `.env.local`). Node 24, OpenSSL and installed Playwright Chromium are required. The ordinary `pnpm test:e2e` suite remains independent and does not start fake authentication.

This explicit opt-in command starts a production Next server and a test-only HTTPS Supabase REST double on ephemeral loopback ports. The double accepts only synthetic `@example.invalid` identities and the synthetic code `123456` after an OTP request. It implements the application's OTP, verify and authenticated user contracts; no email is sent. Each invocation generates a temporary certificate/key under ignored `.auth-e2e/`, trusts that certificate through `NODE_EXTRA_CA_CERTS` for child Node processes, and deletes it on normal completion. TLS verification remains enabled. Production authentication logic has no bypass or fixture adapter.

The browser test exercises account email validation, OTP sign-in, intended-email invitation rejection and recovery, independent-device sign-in to an existing guest identity, relative budgets, separate reminder consent and manual venue confirmation. Browser session cookies are checked for Secure, HttpOnly and SameSite=Lax. This verifies the application against a local provider double, **not live Supabase, actual inbox delivery, provider rate limits or account lifecycle behavior**. Live provider and real-inbox verification remain separate requirements.
